# Flow Notes

The goal is not a simple definition or source summary, but **a model of system behavior understandable from the explanation alone**.
When sources are provided, discard conversation order, investigation history, dead-end hypotheses, and repeated explanations; retain only the behavior ultimately established.

## Principles

1. **Fix one scope.** First establish the boundary of the feature, event, lifecycle, or architecture the user wants to understand. Include subsystems outside that boundary only when the explanation needs them.

2. **Define it on the first line.** One or two lines: `Subject = what it does`.

3. **For behavior flows, use actual execution order and name the actors.** Number temporally ordered actions and prefix each step with `[Actor]`.
   Write "[Server] changes the state to working", not "the state changes".
   Do not force numbering when structural relationships matter more than temporal order.

4. **Place payloads immediately beneath their steps.** Insert an inline code block where important values cross components. Retain only fields that affect the flow explanation.

5. **Connect causes instead of listing actions.** Explain in one line why A makes B possible, rather than merely "B after A". Use "because" or `→`.

6. **Separate easily confused meanings.** Mark distinctions with `※`, especially those explaining bugs or design decisions.
   - A value (path, id) exists ≠ the actual resource (file, process) exists
   - An event occurs ≠ the event is observed
   - Registration requested ≠ registration succeeded
   - Request ≠ response; notification ≠ control
   - **A value supplied by an external system ≠ one generated by our system ≠ an inferred value**

7. **Show both directions when a response changes the caller.** For hooks, callbacks, or request/response flows where a caller waits for a response and changes behavior based on it, show all of `request → processing → response → caller behavior change`. Mark where the caller awaits/blocks.

8. **Label temporary structures as temporary.** If A exists only until B becomes usable, show "start with A → switch to B when B exists" instead of listing A and B as equivalent components.

9. **For architecture questions, begin with responsibilities instead of chronology.** Use a tree to show what each component owns / receives / emits / does not own, then add a short interaction flow.

10. **Avoid long analogies.** Actively use short memory labels such as `fuse`, `ticket`, or `name tag`, in parentheses or comments.

11. **Mark missing evidence.** Tag implementation details unsupported by provided material or verifiable evidence with `[Inference]` or `[Needs verification]`. Do not invent intermediate steps to smooth the narrative.

## Output format

This is the entire default:

```
Subject = one- or two-line definition

1. [Actor] Action
   - Condition / state change / reason, only when needed
   (payload code block)
2. ...
```

Append these sections after the flow **only when needed**. Do not fill them every time.

- Structure: when recurring payloads or components are worth collecting in one place
- Exceptions: when paths outside the normal flow (resume, failure, retry, etc.) matter
- Confusing distinctions: when inline `※` notes are insufficient

## Style

- Concise Korean; retain original technical terms and identifiers
- Arrows for causality; `※` for cautions
- Code blocks only for payloads, states, and short diagrams
- No greetings, praise, repeated conclusions, or lengthy explanatory prose
- State each fact once, even if it appears repeatedly in the source

## Examples

Refer only to the format. Do not copy the domain or terminology.

### Example A — Event flow

````
Automatic access token refresh
= When a request fails because its token expired, obtain a new token with the refresh token and retry the original request.

1. [Client] Make an API request (attach access token)
2. [Server] Detect token expiration → return 401
   ※ Receiving 401 ≠ logout. The refresh token may still be valid
3. [Client] Interceptor catches 401 and holds the original request in a queue (waiting room)
   - If refresh is already underway, only enqueue → prevent duplicate refresh requests
4. [Client → Server] Request refresh
   ```http
   POST /auth/refresh
   ```
   ※ How the refresh credential is supplied (cookie, body, etc.) depends on the implementation
5. [Server] Validate refresh token → issue new access token
   - Revoke the old refresh token (when using rotation)
6. [Client] Save new token → retry queued requests with the new token
   → If the interceptor connects the original request's Promise to the retry result,
     the original caller receives the final retry result

Exception
※ If refresh also fails, fail the entire queue and navigate to the login screen
````

### Example B — Architecture

```
Order notification structure
= The order service only emits events; a worker owns notification delivery.

[Order Service]
├─ Owns: order state
├─ Emits: OrderPaid { orderId, eventId }
└─ Does not own: channel selection, delivery retries

[Queue]
└─ Stores and delivers events (at-least-once)

[Notification Worker]
├─ Receives: OrderPaid
├─ Owns: channel selection (email/push), delivery history
└─ Guarantees: one delivery per eventId

Order Service → Queue → Worker → Email / Push

※ At-least-once means the same event may arrive twice
  → Worker must deduplicate by eventId (idempotency)
```

## Final check

- Did you explain the system rather than the sources or conversation?
- Is it clear what happens first and why the next action becomes possible?
- Is the actor of each action clear?
- Are externally supplied values distinct from internally generated values?
- Did you avoid filling unnecessary sections?
